# RCA — "Essential Gemstones" production "lost all data"

## Verdict
**No data was lost or wiped in production, and no deploy repointed/reset the production database.** Production is on its own separate, managed MongoDB Atlas database (expected Emergent behaviour — preview and prod are always distinct DBs), and that database is **fully populated with real, customized content**. What the user is seeing is a **content divergence between the preview DB and the production DB**, not data loss. This is a data-sync decision, not a bug.

## Evidence (production, active run f9487c5a-8773-423a-b48f-e35819b74190)

### 1. Is production bound to an EMPTY or DIFFERENT DB? → Different (its own), but NOT empty
- Production DB name: **`gemstone-makeover-base`** (resolved + decrypted server-side; separate from preview's local Mongo — this is normal).
- `list_collections` → **12 collections**, all present: `site, users, admins, media, product_waitlist, app_settings, password_attempts, chat_sessions, admin_trusted_devices, payment_transactions, subscribers, admin_email_otps`.
- This is NOT a fresh/empty DB showing `default_site()` output.

### 2. Does `site` have `_id: "main"`, and is it real data or seeded default? → Real data
- `site` collection: **count = 1**, document **`_id: "main"` exists**.
- The document is unmistakably **real, heavily customized content**, NOT generic `default_site()`:
  - 2 products (`Cross of Faith Lava Stone Bracelet` $24, `7 Chakra Lava Stone Bracelet` $28) with live Stripe `buy.stripe.com` URLs
  - 7 chakra stones (Red Jasper → Amethyst) with custom copy
  - A custom section `"My dog"` (`id: my-dog`) — user-authored, cannot be a default

### 3. MONGO_URL / DB_NAME, and did a redeploy reset/re-point it? → No

## Root cause
Preview and production are **separate databases by design**. The user's most recent edits (notably the hero headline "Grounded stones for grounded people.") were made in the **preview** DB and were **never written to the production** `site` document. Production still holds its own (also real, full) content with the older hero wording. Seeing the older hero on the live site — combined with the assumption that preview edits auto-propagate — read as "lost all data," but the production `site` document and all 12 collections are intact.

## Resolution (no source fix required)
To make production match the latest preview content, **copy the preview `site` document (`_id: "main"`) into the production DB** — either:
- **DB Manager → move/copy preview → prod** (Deployment Panel → Database), or
- Re-publish the content from the app's own admin (which issues `PUT /api/site` against production).

There is **no data-loss bug** and **nothing to restore from a backup** — production data is present. This is a one-directional content sync from preview to prod. After syncing, hard-refresh / incognito the live URL to rule out any stale cached bundle.

## What was NOT the cause
- Not an empty/fresh production DB.
- Not a deploy wiping or repointing the DB (migrate step was a no-op).
- Not a stale/old production image (backend + frontend are current).
